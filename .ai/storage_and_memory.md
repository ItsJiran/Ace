# Storage & Event Interactivity Mechanism

The Client Engine relies on a highly decoupled, key-based lookup architecture for state management. This strictly separates persistent application configurations from volatile, high-speed ephemeral data (RAM).

All storage schemas are strictly typed internally using Zod definitions located in `src/schemas/storage.ts`.

---

## 💾 Global Persistent Storage
This is the long-term, disk-persisted state of the application. It acts as the backbone configuration that survives application restarts. 

It is divided strictly to ensure different modules do not conflict:
1.  **Main App Settings**: Core client behaviors (theme preferences, default Gateway selection, hotkeys).
2.  **Installed Widgets & Repositories**: Arrays holding identifiers mapping to the user's downloaded toolkit components.
3.  **Widget Settings (`widget_settings`)**: A nested record keyed by `widget_slug`. Every widget receives an isolated slice of the persistent storage to save context (e.g., API keys for a specific tool or saved user preferences for a specific UI view).

---

## ⚡ Ephemeral RAM Storage Architecture
Because the Engine must orchestrate dozens of rapid, independent interactions between multiple windows, tools, and the AI Gateway, standard nested state trees (like basic Redux/Zustand implementations) become a massive bottleneck.

Instead, the application utilizes a **Key-Based Indexing RAM** mechanism, composed of two flat data structures:

### 1. Global RAM (The Payload Store)
The Global RAM strictly holds pure data separated entirely from its origin context. 
Every piece of data generated by any widget or gateway interaction is given a unique `memory_uid` and dumped into a massive flat object map.
*   **Format**: `Record<memory_uid, Payload>`
*   **Why?**: Ensures identical pieces of data are not duplicated across different widget contexts. Any window or tool can grab the exact payload if they know the `memory_uid`.

### 2. Global Classification RAM (The Index Store)
To actually *find* things in the huge Global RAM, the app uses a secondary indexing structure mapping classification keys to arrays of `memory_uids`.

When a widget creates a memory, it tags the memory under classifications (like indicating its origin widget, its data type, or the interaction involved).
*   **Format**: `Record<classification_string, Array<memory_uid>>`
*   **Example Output**:
    ```json
    {
      "widget_slug:my_calendar_widget": ["mem-001", "mem-005"],
      "type:urgent_notification": ["mem-007"],
      "emitted_by_window:window-abc": ["mem-001", "mem-003"]
    }
    ```

### How 1 and 2 Work Together
If a widget needs all urgent notifications, it performs a 1ms lookup on the Classification RAM for `"type:urgent_notification"`, retrieving `["mem-007"]`. It then uses those IDs to instantly fetch the exact payloads from the Global RAM. 

---

## 🔄 RAM Interactivity Mechanism
Widgets never mutate the RAM directly. They dispatch strictly typed Events using the `RAMInteractivitySchema`.

*   **`create_memory`**: A widget emits a payload alongside an array of classifications. The engine generates a `memory_uid`, saves the payload in Global RAM, and appends the `memory_uid` to every requested key in the Classification RAM.
*   **`update_memory` / `delete_memory`**: The widget interacts explicitly by indicating the target `memory_uid`.
*   **`read_memory`**: A widget can request a specific `memory_uid` or request the engine to resolve an entire `classification_string`.
